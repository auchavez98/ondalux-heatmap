Why open source

Trust the numbers behind the colors

Transparent models

Path loss, wall attenuation, SNR, SINR and the measured-map interpolation are documented formula by formula, with their limitations stated plainly.

An open file format

A .lux project is a ZIP with readable JSON and the floor plan image. Your designs never get locked into a tool you cannot inspect.

A catalog anyone can grow

Every access point model comes from an official datasheet, with its source link. Anyone can propose new models following the same rule.

Under the hood

Fast, native and dependency-light

Written in Rust with an immediate-mode interface (egui) and parallel computation (rayon). A heat map updates in well under 100 ms while you drag an access point, and the whole app is a single portable executable.

  • Pure-Rust PDF import, wall detection and PDF reports
  • Native WiFi scanning on Windows (macOS and Linux in progress)
  • No runtime to install, no telemetry, works offline

Build from source

Three commands

You need Rust {{msrv}} or newer (install it from rustup.rs).

git clone {{github.cloneUrl}}
cd ondalux-heatmap
cargo run --release -p ondalux-app

Run the test suite with cargo test --workspace. On Windows the release build is a single portable ondalux.exe.

Contribute

Ways to help

You do not need to write Rust to make a difference.

  1. 1

    Report problems

    A plan that imports badly, a wall the detector misses, a number that looks wrong: an issue with the file attached helps the most.

  2. 2

    Add access point models

    Send the model with its radio values and the link to the vendor's official datasheet. Values without a source are not accepted.

  3. 3

    Validate with real surveys

    Comparing predictions with measurements in real buildings is the best way to tune material losses.

  4. 4

    Test on macOS and Linux

    The scanning backends compile there but need testing on real hardware.

  5. 5

    Translate

    The app and reports are in English and Spanish; more languages are welcome.

  6. 6

    Write code

    Pick an open issue, keep changes small and run formatting, linting and tests before opening a pull request.
